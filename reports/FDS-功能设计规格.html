1系统结构

前端 (Vue 3 + Element Plus) ├─ 视图层：仪表盘 / 设备 / 控制 / 历史 / 报警 / 工业4.0 / 数据大屏 / 配置 ├─ 传输：REST (axios, Bearer JWT) + WebSocket (socket.io, polling 优先) └─ 打包：Electron 33，页面走 file://，后端由主进程 spawn 后端 (Flask 3.1 + SocketIO/threading) ├─ 展示层 ── 12 个 API 蓝图（170 个端点）+ 页面认证 + 错误处理 ├─ 采集层 ── 设备管理器（30 台模拟/真实设备）、数据采集器、行为模拟器 ├─ 存储层 ── SQLite（WAL 模式），8 张表 ├─ 报警层 ── 规则引擎、去重/抑制、洪水检测、升级、输出（塔灯/广播） ├─ 智能层 ── OEE、预测维护、SPC、能源、边缘决策、设备控制（联锁/急停） └─ core ── 健康检查、熔断、限流、降级、缓存、审计、调度 进程：单后端进程（5000 端口，模拟模式）+ Electron 主进程 部署：托盘常驻，前端与后端同机

6关键设计决策（人工补充，非自动生成）

为什么时间序列化要自定义 JSON Provider：后端大量用 naive datetime（本地时间）， Flask 默认按 HTTP-date 输出成 ... GMT，把本地时间谎报成 UTC，前端解析后 +8 小时。 统一输出带偏移的 ISO8601 是唯一不会错的做法。
为什么采集用「线程 + 批量事务」而不是每点一事务：30 台设备 × 2 秒周期会产生 十几点/秒的写入，逐条提交在 SQLite 上会把 WAL 撑大且拖慢；批量提交 + WAL 才能在 kill -9 时不丢数据 （已由 crash-recovery 演练证实）。
为什么状态量（*_status / *_state）必须离散化：OEE 的可用率依赖设备状态码（0–5）， 连续浮点会被采集器整体丢弃，实时状态跟踪等于空转。这条在模拟器和采集器两侧都要拦。
