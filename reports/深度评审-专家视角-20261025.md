# 深度评审：如果这项目由工业自动化交付团队来做

> 回答四个问题：(1) 顶尖专家会做但你没要求的事 (2) 他们从哪些原始素材入手
> (3) 具体方法和工具 (4) 除你之外谁能证明结果正确
> 最后给出「本次实际补上了什么、哪些没做、为什么」。

先声明一个判断标准，后面所有内容都按它筛：

> **能被第三方独立复核的，才算证据。**
> 自己跑一遍说"通过了"不算；源码读起来"应该没问题"更不算。

## 一、专家会做、但你没要求的事

### 1.1 报警管理按 ISA-18.2 交付，而不是"有报警就行"

ISA-18.2（报警系统管理）对一套报警系统有硬指标，交付时要出**月度 KPI 报告**：

| 指标 | 标准建议 | 为什么要它 |
|---|---|---|
| 平均报警率 | 每操作员 **≤ 6 条/小时**（稳态），峰值 ≤ 12 | 超过这个数操作员会开始忽略报警（ alarm flood 的根因） |
| 高优先级占比 | **≤ 5%** | 全是 critical 等于没有优先级 |
| 频繁/抖动报警 | Top 10 应 < 总报警的 10% | 一条抖动报警能吃掉 40% 的注意力 |
| 陈旧报警（stale） | 应为 0 | 超过 24h 无人处理，说明这条报警没意义 |
| MTTA（平均确认时长） | 按工艺定，但必须**可测量** | 看不出"多久才被确认"，就无法改流程 |

项目现状：`alarm_manager` 已经有洪水检测、优先级矩阵、旁路/搁置、统计器 —— **机制在，但没有一份按标准口径算出来的 KPI 报告**。也就是说"做了引擎，没做仪表"。

### 1.2 数据质量贯穿到人眼看到的地方

OPC UA 的 `StatusCode`、Modbus 的异常码，本质是**"这个值可不可信"**。
工程上最常见的严重缺陷是：传感器坏了、通信超时，系统仍然把**最后一次有效值**当当前值显示，操作员据此做决策。

专家会做的是：
- 每个值带质量戳（Good / Uncertain / Bad / Stale）
- **Bad 的值在 UI 上必须视觉可辨**（灰掉、加删除线、显示 `??`），不能和正常值长得一样
- 质量变化要进事件日志（"14:23:11 PV-101 质量 Good→Bad"）

项目现状：`quality: 192`（OPC UA Good）在数据里，前端也有 `qualityLabel()`，
但**没有做过"坏质量覆盖率"统计** —— 不知道自己有多少点在拿坏数据当好数据用。

### 1.3 时钟：SCADA 里最经典的隐形炸弹

工业现场的时间问题比互联网严重得多：
- 采集端时钟、服务器时钟、数据库时间、前端显示，**四个时间源**
- 夏令时切换那一小时的数据会重复或丢失
- NTP 漂移导致"后到的数据时间戳更早"，历史曲线出现回折
- SQLite 的 `CURRENT_TIMESTAMP` 是 UTC，而业务代码大量用 `datetime.now()`（本地），
  **两者混用必然错位** —— 这个项目就踩过（我在 10-23 修的那批里有一半是时间问题）

专家会做**时钟一致性检查**：不只看"时间对不对"，而是查
「同一条记录里不同时间字段的偏差分布」「跨表同事件的时间差」「回退/跳变检测」。

### 1.4 变化即审计（MOC，Management of Change）

工业系统里"谁把报警阈值从 180 改成 200"必须可查，因为出事时要定责。
项目的 `operation_logs` 记录了操作，但**配置变更没有 diff** —— 只记了"更新了 system 配置"，
没记"哪个键从什么改成什么"。这在等保测评里是硬伤（GB/T 22239 安全审计要求）。

### 1.5 故障注入是必做项，不是加分项

专家不会问"系统能不能跑"，而会问：
- 数据库被杀掉，采集会不会丢数据？丢多少？
- 设备全断，UI 会不会还在显示"在线"？
- 采集线程卡死，健康检查能不能发现？

项目里 `core/chaos_engineering.py` 写好了（有实验、状态机、注入器），
但**全仓没有任何地方调用它** —— 属于"买了消防器材没装"。

### 1.6 备份要验证"能恢复"，不是"有备份"

`auto_backup.py` 会定时备份。但专家会追问：
- 备份文件能打开吗？（完整性）
- 恢复后数据一致吗？（可用性）
- 恢复演练多久一次？（RTO）
- 恢复过程会不会覆盖现场正在用的库？（安全性）

**没做过恢复演练的备份，等于没有备份。**

### 1.7 性能要有基线数字，不是"挺快的"

专家交付时会给出：
- 采集吞吐（点/秒）与 CPU/内存的对应关系
- 端到端延迟（采集 → 入库 → 推送到 UI）的 P50/P95/P99
- 数据库增长速率（GB/天）与保留策略的匹配
- **降级阈值**：多少点/秒开始丢数据

### 1.8 点表核对（这是最容易出人命的一步）

PLC 点表（register map）和 SCADA 配置必须**逐点核对**：
地址、数据类型、字节序、量程、单位、读写权限。
错一个字节序，温度 25.3 会显示成 -1.2e38。

专家会用**脚本自动核对**点表 vs 设备手册，而不是人眼比对 Excel。

### 1.9 报警阈值要有出处

`boiler_temperature > 180°C` 这个 180 从哪来？
- 工艺设计参数（P&ID / 工艺卡片）
- 设备铭牌上限
- 历史数据统计（P99 + 裕量）
- HAZOP 分析结论

**拍脑袋的阈值在评审时一问就露。** 项目里 `配置/alarms.yaml` 的 10 条规则，
注释里没有一条写了出处。

### 1.10 交付物清单

| 文档 | 作用 |
|---|---|
| FDS 功能设计规格 | 每个功能的输入/输出/异常处理 |
| 点表（IO List） | 现场接线与组态的桥梁 |
| SAT 现场验收测试记录 | 逐条测试、签字 |
| 运维手册 | 常见故障处置 |
| 培训记录 | 操作员会用 |

毕设里不可能全做，但**FDS 的核心章节 + SAT 的测试记录表**是能做的。

## 二、专家从哪些原始素材入手

不是"安全、易用"这种形容词，而是**具体的、能被引用的东西**：

| 素材 | 具体形态 | 在本项目里对应什么 |
|---|---|---|
| **P&ID 工艺流程图** | 设备位号（K-101、E-102）、管线、控制回路 | `devices.yaml` 里的 30 台设备应该有位号来源；`alarms.yaml` 的阈值应该标在 P&ID 上 |
| **设备铭牌 / 数据手册** | 量程、精度、响应时间、寄存器地址表 | `registers` 的 `scale`、`data_type`、`unit`、`min/max` 应来自手册 |
| **Modbus/OPC UA 点表** | Excel 或 CSV，一行一个点 | 应当能导出成点表并和设备手册核对 |
| **历史工况数据** | 正常/异常工况的运行记录 | 用来定报警阈值（P99）和趋势基线 |
| **HAZOP / 故障树** | 偏差 → 原因 → 后果 → 现有防护 → 建议 | 决定联锁规则（`interlocks.yaml`）该有哪些 |
| **SOP 操作规程** | 开停车步骤、异常处置 | 决定哪些操作要二次确认、哪些要联锁禁止 |
| **标准条文** | GB/T 22239（等保2.0）、GB/T 35718（电力监控防护）、ISA-18.2、IEC 62443 | 代码里引用了这些标准编号，但**没有落到具体条款号** |

**这里有一条硬要求**：项目 README 里写的"符合等保2.0 GB/T 22239"，
如果拿不出"哪一条 → 哪个实现 → 哪份证据"，就是空话。
本次要做的就是把这段话变成表。

| 目的 | 方法 | 工具/命令 |
|---|---|---|
| 报警 KPI | ISA-18.2 口径统计（率、Top N、stale、MTTA） | 自己写脚本扫 `alarm_records` 表，输出可打印报告 |

| 协议一致性 | 与标准报文比对 | Wireshark / `modbus-cli` 抓包 |

## 四、除你之外，谁能证明结果是对的

这一节最关键。**自证不算证。**

| 证据来源 | 具体是什么 | 为什么算"第三方" |
|---|---|---|
| **标准条文本身** | ISA-18.2 的 6 条/小时、5% 高优先级 | 数字是别人定的，你只需证明自己落在区间内 |
| **公开基准数据集** | Tennessee Eastman Process（化工过程控制的标准 benchmark） | 全世界用它对比，结果可横向比 |
| **协议一致性测试** | Modbus Conformance Test / OPC UA Compliance Tool | 由协议基金会维护 |
| **物理守恒律** | 物料平衡、能量平衡 | 自然定律，不认人 |
| **统计检验** | 数据不能是白噪声（Ljung-Box）、不能有趋势漂移（Mann-Kendall） | 检验方法本身有标准 |
| **独立复现** | 别人拿到仓库，按 README 一条命令复现同样结果 | 可复现性 = 科学方法的底线 |
| **时间戳的外部锚点** | 与 NTP 服务器、与系统 `date` 命令比对 | 外部时钟 |
| **别人的代码/工具** | `sqlite3 integrity_check`、`pymodbus` 的解析结果 | 不是自己写的 |

**能同时用上"物理守恒 + 统计检验 + 独立复现"三样的项目，说服力和"我跑了一遍没报错"完全不是一个量级。**

## 五、本次实际做了什么（以及没做什么）

下面这部分是**真正落地的**，每条都有可运行的东西和可查看的产物。
原则：**宁可少做，也要每条都能被别人复核。**

（详细结果见 `深度交付-证据清单.md`；本节只列结论。）

| # | 事情 | 状态 | 证据形态 |
|---|---|---|---|
| 1 | ISA-18.2 报警 KPI 报告 | ✅ 做 | `tools/isa18-kpi.js` → 输出 JSON + 可打印 HTML |
| 2 | 数据质量覆盖率审计 | ✅ 做 | `tools/data-quality-audit.js` → 质量分布 + 坏值点位清单 |
| 3 | 时钟一致性审计 | ✅ 做 | `tools/clock-audit.js` → 跨字段偏差、回退检测 |
| 4 | 故障注入演练（断连） | ✅ 做 | `tools/fault-drill.js` → 演练记录 |
| 5 | 数据完整性（kill -9 恢复） | ✅ 做 | `tools/crash-recovery-drill.ps1` → 丢数据计数 |
| 6 | 点表核对（配置 vs 实际读写） | ⚠️ 部分 | 只能核对模拟器；真实设备需现场 |
| 7 | 物理量平衡自检 | ❌ 没做 | 模拟数据不满足守恒，做出来是假证据 |
| 8 | 报警阈值出处表 | ⚠️ 部分 | 能列出「无出处」的清单，定不了阈值（需工艺） |
| 9 | 配置变更 diff 审计 | ❌ 没做 | 要改后端存储结构，属主仓范围 |
| 10 | FDS/SAT 文档 | ⚠️ 部分 | 只出模板 + 已实现部分的填写 |

**为什么 7 和 9 不做**：
- 7（物料平衡）：30 台设备各说各的模拟数据，没有真实的物料流关系，算出来的"平衡"是我编的，
  这种证据比没有更糟——它会给评审一个"看起来很专业但其实假的"印象。
- 9（配置 diff）：需要改 `operation_logs` 的表结构和写入路径，属于后端主仓正在动的区域，
  我在补丁层做会冲突。

## 六、一条自我约束

上面所有"✅"的项，验收方式是：

```bash
# 任何人拿到仓库，都能跑出同样的数字
node tools/isa18-kpi.js            # 报警 KPI
node tools/data-quality-audit.js   # 数据质量
node tools/clock-audit.js          # 时钟一致性
node tools/fault-drill.js          # 故障注入
powershell -f tools/crash-recovery-drill.ps1   # 崩溃恢复
```

**如果我给你的数字你复现不出来，那这个数字就是假的。** 这是我给自己定的线。
