# 深度交付：如果这活交给工业自动化交付团队

> 这份文件回答四个问题，并且只回答这四个：
> **(1) 顶尖专家会做哪些你没要求的事　(2) 他们从哪些最原始的素材入手
> (3) 用什么方法和工具　(4) 除了你我，还有什么能证明结果是对的**
>
> 上一版（`reports/深度评审-专家视角-20261025.md`）回答的是"该做什么"——
> ISA-18.2 的 KPI、FDS、SAT、点表核对。那是对的，但**只是清单**。
> 这一版回答的是另一层：**凭什么相信清单上的每一项真的成立**。
>
> 一句话区别：上一版是"我做了体检"，这一版是"我证明这台秤能称出病"。

## 零、先立判据，否则下面全是形容词

> **能证明你错的，才算证据。只能证明你对的，是营销。**

一条检查如果从来没有失败过，它的"通过"没有任何信息量。所以本项目的每条
结论都必须能通过下面三道门：

| 门 | 要求 | 反例（本项目上一轮踩过的） |
|---|---|---|
| 门 1 | 结论来自**可被重算的数字**，不是叙述 | "已按 ISA-18.2 实现" ☠ |
| 门 2 | **检测器本身**被证明会失败（负向控制） | 报警 KPI 在只有 1 条报警的库上"达标" ☠ |
| 门 3 | 第三方能**用自己的机器**重算出同一结果 | 运行库被 `.gitignore` 排除，别人无法复现 ☠ |

三条门全过，才在追溯矩阵里记 `verified`。

## 一、专家会做、但你没要求的事

你没要求的事，不是"再加个功能"——那是把项目做大。以下是**把项目做深**：

### 1.1 先证明"检查会失败"，再谈"检查通过"

这是全套里最反直觉、也最没人要求的一件。专家的顺序是：

```
先播种一个已知缺陷 → 看检测器能不能抓到 → 抓不到就重写检测器
（而不是）先跑检测器 → 看到绿色 → 写进报告
```

本项目落地为 `tools/deepcheck/negative_control.py`：8 个检测器 × 8 个
**具体的**缺陷（陈旧报警、critical 占比 30%、抖动 8 次/小时、20% 质量坏、
500 行 ts_utc 多减 2 小时、字节序配错、备份中段写坏、审计日志被篡改）。
每个缺陷都要求"干净快照 = PASS、播种后 = FAIL、**且报出预期的那条 finding code**"。
只报 FAIL 不算——"失败"可能是因为查错了表。

结果：**8/8**。`reports/deep/negative-control.json` 里有每一格的原始记录。

### 1.2 给证据分级，并主动把自己的结论降级

专家不会把所有"我验过了"写成一样的。他们会分：

| 级别 | 含义 | 谁能复核 |
|---|---|---|
| **A** | 机器可判定，第三方重跑得到同一结论 | 任何人，一条命令 |
| **B** | 结论正确但依赖现场数据/环境，换环境要重测 | 有同类环境的人 |
| **C** | 自己声明，无外部可核对的锚点 | 只能信或不信 |

上一轮 22 条需求里有 16 条标"verified"。**按 A/B/C 重判后，其中 6 条其实只能算 B**
（依赖现场库、依赖后端在跑、依赖那次的手工操作）。主动降级的价值在于：
评审知道该重点看哪几条，而不是被一片绿色骗过去。

### 1.3 写"不能证明什么"清单

专家交付时会有一节叫 **Limitations / Out of scope**。不是免责声明，是
**精确的能力边界**，让下一个人知道该在哪里接手：

- 哈希链**抓不到尾部截断**（删掉最后几条，链内自洽）；
- 运行库里的报警样本只有 1 条，**报警 KPI 在统计上不可判定**（不是"达标"）；
- 模拟数据不满足物料守恒，**不能做物料平衡校验**（做了就是编）；
- 点表只核对了配置↔解码器，**真实设备手册的寄存器表必须现场比对**；
- 备份能恢复 ≠ 恢复后业务正确（只验证了完整性与行数）。

把这些写出来，比多写三个功能更能提高可信度——因为评审第一件事就是找边界，
你主动给出，他就知道你不是在糊。

### 1.4 用可复现的夹具替代"我这台机器上的库"

运行库 100 MB 且被 `.gitignore` 排除。这意味着"请克隆仓库自己验"是个谎。
专家的做法：做一个**结构相同、规模小两个数量级、种子固定**的夹具
（`tests/fixtures/evidence.db`，2.3 MB），让结论与现场数据脱钩。

> 夹具检验的是"仪器有没有分辨力"，不是"现场健不健康"。
> 这两件事必须分开说 —— 混在一起就是把测试数据当生产数据。

### 1.5 阈值要有推导过程，不能是"我觉得 2 分钟够了"

本项目的时间容差不是拍的：

```
实测 315146 行 → 99.995% 的 ts_utc 与 created_at 完全同秒
              → 17 行因队列缓冲晚了最多 628 秒
              → 取 3600 秒 = 实测最大值的 5.7 倍
```

写在 `deepcheck/detectors.py:LAG_MAX_SEC` 的注释里。任何看到这个数字的人
都能判断这个阈值合不合理——而不是只能接受。

### 1.6 变更即审计，且审计日志本身要防篡改

"记录了谁改了配置"是普通要求；专家多走一步：**日志被改也要能发现**。
落地方案是哈希链（`core/audit_chain.py`），并用 9 个篡改手法对抗测试
（改值/改操作人/删中间/调顺序/截尾/键序/空记录/接口契约…）。

### 1.7 点表用"哨兵值"，不用"读一遍看着对"

`0` 和 `0xFFFFFFFF` 在四种字节序下都一样——用它们做测试等于没测。
专家挑**字节不对称**的值：`1.0 / 0.1 / 25.3 / -273.15 / 1234.5678 / -0.0625`，
任何一个字节错位都会变成另一个数。

### 1.8 时钟用"双源交叉"而不是"我对了一遍"

`history_data.created_at` 是 **SQLite 自己写的** `CURRENT_TIMESTAMP`（UTC）。
应用换算出的 `ts_utc` 若与它对得上，说明换算正确；对不上，说明方向错了。
**两个独立来源互证**，比"人眼核对"强一个数量级。

## 二、专家从哪些最原始的素材入手

不是"安全、易用"这种形容词。形容词不能证伪，也不能写进测试。

专家从**不可否认的事实**入手，按"离人最远"排序：

| 层级 | 素材 | 为什么它是原始的 | 本项目如何用 |
|---|---|---|---|
| L0 | **线上的两个 16 位寄存器** | 设备的全部真相就是这 32 个 bit | `encode_words()` 按 Modbus 规范重编，与被测解码器差分 |
| L0 | **SQLite 自己写的 `CURRENT_TIMESTAMP`** | 第三方实现，不是我们的代码 | 与 `ts_utc` 交叉验证，实测差 0.4 秒 |
| L0 | **SHA-256 / git 对象哈希** | 数学，不认人 | 审计链 + 证据清单 |
| L1 | **设备手册的字节序声明**（`ABCD/BADC/CDAB/DCBA`） | 厂商写的，不是我们猜的 | `devices_modbus_sim.yaml: byte_order: ABCD` |
| L1 | **SI 量纲**（无量纲必须显式写 `1`） | 国际单位制 | 3 个点因此被发现缺单位并补齐 |
| L2 | **标准里印好的数字**（ISA-18.2：≤6 条/小时、critical ≤5%） | 别人定的，我们只能落在区间内 | `ALARM_RATE_MAX` / `CRITICAL_SHARE_MAX` |
| L2 | **ISO 8601 的时区偏移语义** | 规范 | 存储 UTC / 传输带偏移 / 展示本地 |
| L3 | **实测分布**（入库延迟直方图） | 数据自己说的，不是我们设的 | 推出 3600 秒阈值 |

**关键点**：L0 之前没有"需求文档"。专家最先打开的是**设备手册的寄存器表**和
**一段真实报文**，而不是需求评审会纪要。因为需求会写错，字节不会。

本项目里最能说明问题的一个数字：

```
history_data.timestamp - created_at = 8.000031 小时（315146 行，标准差≈0）
```

标准差≈0 意味着这不是"时钟慢了一点"，而是**两个时间基准**（本地 vs UTC）。
这个结论不需要看代码，看数据就能得出——这就是"从原始素材入手"的意思。

## 三、方法和工具

### 3.1 方法（按"能证伪的强度"排序）

| 方法 | 干什么 | 为什么强 |
|---|---|---|
| **负向控制 / 故障播种** | 故意造缺陷，看检测器报不报 | 直接证明"仪器有效"，而不是"结果好看" |
| **差分测试** | 两套独立实现算同一个量，比对 | 两套都错成一样，概率极低 |
| **哨兵值** | 用字节不对称的输入打边界 | 平凡值测不出错位 |
| **双源交叉验证** | 应用算的 vs 数据库自己写的 | 不依赖单一实现的可信度 |
| **不变量校验** | `lag ∈ (-60s, 3600s]`，逐行成立 | 一条 SQL 覆盖 31 万行 |
| **计数量而非均值** | 数"多少行越界"而非"平均偏差" | 均值会稀释局部缺陷（500/20000 行偏 2h → 均值只动 180s） |
| **幂等迁移 + 前置备份** | 迁移可重跑、可回滚 | 时间迁移方向搞反是灾难级错误 |
| **哈希链** | 每条记录带前一条的哈希 | 篡改必留痕（除尾部截断） |
| **契约检查（AST）** | 断言接口真的调了审计记录 | 防止"功能还在、调用被删" |
| **可复现夹具** | 固定种子的小库 | 让结论脱离现场环境 |

### 3.2 工具（都用现成的，不自己发明轮子）

| 工具 | 用途 | 谁写的 |
|---|---|---|
| `struct`（Python 标准库） | float32 编解码，参考实现的底座 | 标准库 |
| `sqlite3` | `VACUUM INTO` 一致快照、`PRAGMA integrity_check`、`backup()` | SQLite 官方 |
| `hashlib.sha256` | 审计链、证据清单 | 标准库 |
| `importlib` | 直接加载**正在跑的那份**被测模块（不复制代码） | 标准库 |
| `ast` | 接口契约静态检查 | 标准库 |
| `git rev-parse` | 把代码版本锚进清单 | git |
| `argparse` | 每个工具都有 `--json`，便于机器复核 | 标准库 |
| `pymodbus` / `nmap` / `wireshark` | **未用**（模拟模式无真实总线），列为现场阶段工具 | — |

刻意**不引入**任何测试框架依赖：`python tools/deep-verify.py all` 在裸
Python 3.10+ 上就能跑。理由：验收现场装不上 pip 是常态。

## 四、除了你我，谁能证明结果是对的

这一节是核心。**自证不算证。** 本项目用到的"外部证人"分四类：

### 4.1 别人定的数字（标准）

| 数字 | 出处 | 本项目落点 |
|---|---|---|
| 报警率 ≤ 6 条/小时/操作员 | ANSI/ISA-18.2-2016 | `ALARM_RATE_MAX` |
| critical 占比 ≤ 5% | 同上 | `CRITICAL_SHARE_MAX` |
| 陈旧报警 = 0 | 同上 | `STALE_HOURS=24` |
| 审计记录应受保护、避免被删改 | GB/T 22239-2019 8.1.4.3 | 哈希链 |
| float32 字节序 4 种排列 | Modbus 应用协议规范 | `encode_words/decode_words` |

我们不定义这些数字，只证明自己落在区间内，或者**证明自己落不进去**（见第五节）。

### 4.2 别人写的实现（不共享我们的 bug）

| 实现 | 我们用它对什么 |
|---|---|
| SQLite `PRAGMA integrity_check` | 备份是否真的完整（不是"文件存在"） |
| SQLite `CURRENT_TIMESTAMP` | 与应用的 UTC 换算交叉验证 |
| Python `struct` | 参考解码器，独立于被测代码 |
| SHA-256 | 链的不可伪造性 |
| git 对象哈希 | 代码版本锚点 |

### 4.3 自然律与数学（不认人）

- **时间不可逆**：采样不可能发生在入库之后 → `lag < -60s` 必为错，无需讨论；
- **字节序是双射**：四种排列两两不同，错位必然改变数值 → 哨兵值必能分辨；
- **哈希抗碰撞**：改一个字节，链必断。

### 4.4 别人重跑（科学方法的底线）

```bash
python tools/make-evidence-fixture.py     # 生成 2.3MB 夹具（固定种子）
python tools/deep-verify.py all           # 一条命令，输出 verdict.json
python tools/audit-chain-selftest.py      # 9 个篡改对抗用例
python tools/evidence-manifest.py --verify # 核对：这份代码就是清单里那份
```

`reports/deep/verdict.json` 里的 `certification` 是机器判定的，不是人写的：

```
certification = (负向控制 8/8) AND (审计链自证 9/9) AND (时间基准 PASS) AND (点表 PASS)
```

### 4.5 这些证据**不能**证明什么

写在这里，是为了让评审不必自己去找漏洞：

| 不能证明 | 为什么 | 谁能补 |
|---|---|---|
| 真实 PLC 的寄存器表与本项目配置一致 | 无真实设备 | 现场用同一套脚本跑 `--config` |
| 报警系统健康 | 库里只有 1 条报警，统计上不可判定 | 连续运行 30 天后重跑 KPI |
| 物料/能量守恒 | 模拟数据无物料流关系 | 接真实工艺数据 |
| 长期稳定性（7×24） | 未做长时运行 | 现场试运行 |
| 恶意攻击者拿到数据库写权限后重算整条链 | 哈希链无外部锚点时会被整体重写 | WORM 存储 / 外部时间戳服务 |
